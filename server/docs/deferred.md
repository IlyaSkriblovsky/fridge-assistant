# Отложенное

Упрощения, на которые сервер пошёл сознательно, чтобы быстрее заработать.
Для каждого записано, чем его заменить и когда. Решённые пункты отсюда
удаляются.

Здесь не открытые вопросы, а уже принятые решения. Открытые вопросы — в
[open-questions.md](open-questions.md). У прошивки есть такой же список, её
`docs/deferred.md`.

| Сейчас | Потом | Когда менять |
| --- | --- | --- |
| Прибор использует HTTP | HTTPS для аудио и дашборда | По отдельному решению возобновить переход; отложено после E2 2026-09-23 |
| Сбой сервера приходит на прибор как обычный ответ | Ответ с признаком ошибки и текстом | Когда возьмёмся, меняется контракт с прошивкой |

## Ошибки как обычный ответ

Контракт знает только два исхода: ответ `200` со строковым `response` прибор
показывает как ответ, а всё остальное — как свою ошибку без подробностей. Если
Gemini вернул ошибку или сервер не смог до него достучаться, пользователь
получает обычный ответ с текстом «Gemini ответил ошибкой 400, попробуй ещё
раз». Если не сработал Keep, модель сама говорит об этом в ответе.

Хочется, чтобы сервер мог ответить именно ошибкой, но с текстом: прибор
показал бы её как ошибку, например на своём экране ошибок, и приложил бы
объяснение сервера. Для этого меняется контракт с прибором, а значит, оба
проекта.

## HTTPS между прибором и сервером

Сервер живёт на арендованном сервере
([vision.md](vision.md#сервер-живёт-на-арендованном-сервере)) и доступен из
интернета. Прибор предъявляет ему токен
([vision.md](vision.md#один-пользователь-один-прибор-один-токен)), но ходит пока
только по HTTP, так что токен идёт открытым текстом. Поэтому за nginx-proxy
сервер отвечает и по HTTP ([server.md](server.md#за-nginx-proxy)).

Прибор просыпается ради каждого вопроса, и TLS-рукопожатие он будет платить
каждый раз. [E2](../../firmware/docs/experiments/e2-https-overhead.md#e2----https-overhead)
измерен 2026-09-23 на продакшн-сервере: при хорошем WiFi короткий запрос занимает
по медиане 265 мс по HTTP и 1062 мс по HTTPS с проверкой сертификата. Основная
прибавка — около 0,8 с при установке соединения; после четырёхсекундного
аудиопотока задержка составляет 76 и 80 мс. TLS требует дополнительно около
53 КиБ внутренней памяти. На длинной команде соединение может установиться
во время речи; для короткой команды и дашборда эта задержка заметнее.

**Решение пользователя от 2026-09-23:** переход пока отложить, оставить HTTP.
Эксперимент E2 завершён, результаты сохранены; D5 остаётся в отложенном.
Возвращаемся к реализации по отдельному решению. При переходе нужно настроить
доверенные сертификаты и часы для обоих клиентов прибора и проверить обычную
прошивку на коротких/длинных командах и загрузке дашборда. Энергопотребление в
этом опыте не измерялось.
