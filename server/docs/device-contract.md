# Контракт с прибором

Первоисточник — прошивка: `docs/project-vision.md` (раздел «The request
contract») в `../sticky-test-2`. Здесь то же самое, но с точки зрения сервера.
Если контракт меняется, он меняется в обоих проектах сразу.

Здесь только сам контракт. То, что прошивка пока не умеет и сколько она ждёт
ответа, — это её недоработки и настройки, а не ограничения сервера. Прошивку
подгоняют под сервер, а не наоборот. Исключений сейчас нет: кириллицу прибор
рисует, длинный ответ переносит по словам.

## Запрос

```
POST /audio
Authorization: Bearer <токен>
Content-Type: audio/wav
Transfer-Encoding: chunked

<WAV: PCM, 16 kHz, mono, signed 16-bit little-endian>
```

- **Тело идёт потоком, пока кнопка зажата**, подробнее в следующем разделе.
- **Оба поля длины в WAV-заголовке равны `0xFFFFFFFF`**, потому что заголовок
  уходит раньше, чем запись получает длину. Настоящую длину сервер берёт из
  конца chunked-тела. `0xFFFFFFFF`, а не ноль, потому что Python `wave` читает
  такой файл как файл неизвестной длины, а ноль отвергает как `not a WAVE file`.
- **Поток может оборваться посередине.** Тогда до сервера доходит обрезанное
  тело, и прибор уже показывает ошибку.
- **Токен статичный и общий у прибора и сервера**: `kDeviceToken` в
  `src/secrets.h` прошивки и `DEVICE_TOKEN` у сервера, см.
  [vision.md](vision.md#один-пользователь-один-прибор-один-токен). Без него
  сервер дочитывает тело и отвечает `401`, прибор показывает
  `SERVER ERROR 401`.

## Звук приходит потоком

Запрос открывается, как только прибор подключился к WiFi и нажатие длится
достаточно долго, чтобы считаться вопросом. Дальше звук уходит на сервер по
мере записи, пока пользователь ещё говорит. Последний (нулевой) chunk означает,
что вопрос закончен. Отдельного сигнала «я всё» нет.

Поэтому сервер может не ждать конца вопроса: входящий поток можно сразу
передавать во внешний сервис, например в потоковое распознавание речи. Тогда к
моменту, когда пользователь отпустил кнопку, большая часть работы уже сделана,
и после этого остаётся дослать последние куски и дождаться результата. Конец
входящего потока становится сигналом «звук закончился» для внешнего сервиса.

Параметры звука известны с первых байт: они в WAV-заголовке, который приходит
первым. Если внешнему сервису нужен сырой PCM, заголовок можно отрезать.

Если перед сервером когда-нибудь встанет прокси, у него должна быть выключена
буферизация тела запроса (в nginx `proxy_request_buffering off`). Иначе поток
незаметно превратится в обычный POST, и всё это преимущество пропадёт.

## Ответ

```json
{ "response": "текст для экрана" }
```

Прибор читает только поле `response`, остальные поля игнорирует.

Текст он переносит по словам сам, так что перевод строки в ответе — это
намеренный разрыв абзаца, а не то, чем разбивают длинную фразу. На экран
помещается семь строк 24 pt, примерно 375 байт русского текста; что не
влезло, обрывается многоточием, и сервер об этом никак не узнаёт. Длину
ответа держит системный промпт, а не контракт.

Любой ответ 200 со строковым `response` прибор считает успехом и просто
показывает текст. Если серверу есть что сказать об ошибке (не понял вопрос,
внешний сервис недоступен), он говорит это текстом в `response`. Ответить
именно ошибкой, но с текстом, сервер пока не может, это отложено
([deferred.md](deferred.md#ошибки-как-обычный-ответ)).

## Что видит пользователь при сбое

| Что случилось | Экран |
| --- | --- |
| Сервер недоступен или соединение умерло посреди запроса | `NO SERVER` |
| Ответ не 200 | `SERVER ERROR` и код |
| Ответ не JSON или в нём нет строкового `response` | `BAD RESPONSE` |
| Прибор не дождался ответа | `TIMED OUT` |

Сколько прибор ждёт ответа, задаёт `kResponseTimeoutMs` в `src/config.h`
прошивки. Если серверу понадобится больше, это значение увеличивают.

Чтобы вызвать эти случаи нарочно, у сервера есть отдельные эндпоинты:
[server.md](server.md#намеренные-сбои).
