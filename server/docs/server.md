# Сервер: как устроен сейчас

Прототип. Пока умеет одно: принять WAV с прибора, положить его на диск и
ответить фиксированной фразой. Ни распознавания речи, ни AI, ни интеграций ещё
нет.

Весь код в `main.py`: FastAPI-приложение, запускается через uvicorn. Зависимости
в `pyproject.toml`, ставятся через `uv`.

## Запуск

```sh
uv sync
uv run python main.py
```

При старте сервер печатает адрес, который нужно вписать в прибор
(`kBackendBaseUrl` в `src/config.h` прошивки):

```
  Put this URL into the device (same WiFi network):
    http://192.168.1.42:8000/audio
  Public IP (needs port forwarding to be reachable): 203.0.113.7
```

Прибор в той же WiFi-сети ходит по локальному адресу. Публичный IP печатается
на случай, если понадобится доступ снаружи. Сам по себе он не заработает, нужен
проброс порта на роутере.

Переменные окружения:

| Переменная | По умолчанию | Что |
| --- | --- | --- |
| `HOST` | `0.0.0.0` | Адрес, который слушает сервер |
| `PORT` | `8000` | Порт |
| `RECORDINGS_DIR` | `recordings` | Куда сохранять записи. Каталог в `.gitignore` |

## `POST /audio`

Тело запроса — это WAV. Content-Type не проверяется. Multipart-форма с файлом
тоже принимается, если прошивке так удобнее. Сейчас прошивка шлёт сырое тело,
см. [device-contract.md](device-contract.md).

Тело пишется на диск кусками по 64 КБ по мере прихода и целиком в памяти не
держится. Прибор шлёт его потоком (`Transfer-Encoding: chunked`), пока кнопка
ещё зажата, поэтому в момент отправки заголовка длина записи неизвестна, и оба
поля длины в WAV-заголовке приходят как `0xFFFFFFFF`. Когда тело пришло
целиком, `settle_wav_lengths()` вписывает настоящие длины. Трогает она только
поля, равные `0xFFFFFFFF`, а чанк `data` ищет обходом чанков, а не по смещению
36. Если поток оборвался (`ClientDisconnect`), в файле остаётся то, что успело
прийти, и длины вписываются так же.

Файл сохраняется как `recordings/YYYYMMDD-HHMMSS-mmm.wav`. Ответ:

```json
{
  "status": "ok",
  "filename": "20260915-163045-123.wav",
  "bytes": 64044,
  "response": "Received 64044 bytes"
}
```

Прибор показывает только `response`. Остальные поля нужны для проверки через
`curl`.

В консоль пишется размер, время прихода тела и разобранный WAV-заголовок. По
нему видно, с какими параметрами прибор на самом деле пишет звук:

```
[20260915-163045-123] 20260915-163045-123.wav  64044 bytes chunked over 2.31 s  content-type=audio/wav  16000 Hz, 1 ch, 16-bit, 2.00 s  (lengths filled in)
```

Если заголовка нет (сырой PCM), в логе будет `not a readable WAV`, но файл всё
равно сохранится. Если поток оборвался, в конце строки будет `-- the device
went away before the end`.

### Проверка

```sh
curl -X POST --data-binary @sample.wav -H "Content-Type: audio/wav" \
  http://localhost:8000/audio
```

## Намеренные сбои

Прошивка различает четыре плохих исхода запроса: `NO SERVER`, `SERVER ERROR`,
`BAD RESPONSE`, `TIMED OUT`. Три из них от работающего сервера получить
невозможно, поэтому для них есть отдельные эндпоинты. Они ничего не сохраняют:

| Эндпоинт | Что делает | Что показывает прибор |
| --- | --- | --- |
| `POST /audio/fault/500` | Отвечает `500` | `SERVER ERROR 500` |
| `POST /audio/fault/empty` | Отвечает `200` и `{}` | `BAD RESPONSE` |
| `POST /audio/fault/slow` | Молчит `FAULT_DELAY_SECONDS` (45 с) | `TIMED OUT` |

Для `NO SERVER` сервер вовсе не нужен: прошивка сама стучится на закрытый порт
и на адрес, где никого нет.

Все три эндпоинта дочитывают тело запроса до конца, прежде чем ответить (это
делает `drain()`). Иначе соединение закроется под прибором, который ещё не
закончил загрузку, и он покажет `NO SERVER` вместо проверяемого случая.

`FAULT_DELAY_SECONDS` должна быть больше `kResponseTimeoutMs` прошивки (сейчас
30 с), чтобы прибор сдался первым. Если в прошивке таймаут увеличат, это
значение нужно поднять вслед за ним.

## Устройство `main.py`

| Что | Зачем |
| --- | --- |
| `lan_ip()`, `public_ip()` | Адреса для подсказки при старте |
| `lifespan()` | Создаёт каталог записей и печатает адреса |
| `upload_audio()` | `POST /audio` |
| `settle_wav_lengths()` | Вписывает длины в заголовок потокового WAV |
| `describe_wav()` | Строка с параметрами WAV для лога |
| `drain()`, `fault_*()` | Намеренные сбои |

`UploadFile` импортируется из `starlette.datastructures`, а не из `fastapi`.
Парсер формы отдаёт starlette-овский класс, и `isinstance` по fastapi-шному
подклассу не поймал бы ни одного файла.
