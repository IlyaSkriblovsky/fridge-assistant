# Telegram-бот

Решения согласованы 2026-10-06. Реализация ещё не начата: документ описывает
целевое поведение, а не возможности текущего сервера.

## Назначение и границы

Telegram — ещё одна поверхность общения с тем же семейным ассистентом.
Допущенный пользователь отправляет текст или голосовое сообщение, Gemini
выполняет запрос существующими инструментами и отвечает текстом.

Обе поверхности используют одну модель, одни описания функций и обработчики,
общий список покупок и общие напоминания. Отдельных учётных записей,
персональных данных ассистента и новых инструментов не добавляем.

Каждое сообщение — самостоятельный запрос без истории переписки, как каждое
голосовое нажатие на приборе. Ответ на предыдущее сообщение в Telegram сам
по себе не добавляет его в контекст Gemini. Напоминания, созданные через
Telegram, срабатывают на приборе по существующему механизму.

Групповые чаты, история диалога, семейные записки, отправка сообщений другим
людям по команде ассистента, уведомления о батарейке и доставка напоминаний
на телефон не входят в эту версию.

## Библиотека и запуск

Используем `python-telegram-bot` с асинхронным интерфейсом и long polling.
Бот работает в том же процессе и Docker-контейнере, что и FastAPI. Сервер
сам получает сообщения от Telegram; новый HTTP-эндпоинт, webhook и изменения
nginx не нужны.

Запуск и остановка входят в существующий `lifespan` FastAPI. Жизненным
циклом библиотеки и polling управляем явно, без `run_polling()`. На один
токен запускается один polling-процесс; несколько воркеров с одним ботом
не предусмотрены.

Адаптер вызывает общий код ассистента и дашборда напрямую, без HTTP-запросов
сервера к самому себе.

## Настройки и доступ

```dotenv
TELEGRAM_BOT_TOKEN=...
TELEGRAM_ALLOWED_CHAT_IDS=123456789,987654321
```

- Без `TELEGRAM_BOT_TOKEN` Telegram выключен, прибор работает как обычно.
- `TELEGRAM_ALLOWED_CHAT_IDS` — числовые Chat ID через запятую. При заданном
  токене пустой или некорректный список — ошибка настройки при старте.
- Принимаем только личные сообщения: разрешённый Chat ID обозначает разговор
  с допущенным пользователем. Группы и каналы не поддерживаем.
- Тип чата и Chat ID проверяем до скачивания аудио и обращения к Gemini,
  в том числе для `/dashboard`. На недопущенные сообщения не отвечаем,
  но записываем неизвестный Chat ID и тип чата в серверный лог.

Чтобы добавить члена семьи, он открывает бота и нажимает Start. Сервер
логирует отказ до скачивания файлов и вызова модели, например:

```text
[telegram] access denied: chat_id=123456789 chat_type=private
```

Оператор берёт Chat ID из лога, добавляет в `TELEGRAM_ALLOWED_CHAT_IDS`
и перезапускает сервер. Для первоначальной настройки, когда бот ещё
не запущен, ID можно получить методом Telegram `getUpdates` после нажатия
Start. Пустой список допуска по-прежнему не позволяет запустить бота.
В записи об отказе не сохраняем текст сообщения, аудио или токен бота.

Регистрации, паролей и диалога авторизации нет. Список допуска задаётся
оператором через окружение; изменения применяются после перезапуска.
`DEVICE_TOKEN` продолжает защищать все существующие HTTP-эндпоинты.

## Обработка сообщений

В `assistant.py` остаётся один цикл `generateContent` и выполнения тулов.
Обобщаем его вход: текст либо аудиобайты с MIME-типом.

| Источник | Вход в Gemini | Ответ |
| --- | --- | --- |
| Прибор, `POST /audio` | WAV, как сейчас | Существующий HTTP-ответ для экрана |
| Telegram, текст | Текстовая часть | Текстовый reply на исходное сообщение |
| Telegram, голосовое | Аудио с соответствующим MIME-типом | Текстовый reply на исходное сообщение |

Голосовое скачиваем в память. OGG/Opus передаём непосредственно в Gemini,
без отдельного распознавания и конвертации в WAV. Сервер не сохраняет аудио
на диск. Ограничиваем размер загрузки, проверяя заявленный размер и фактически
полученные байты; превышение отклоняем до вызова модели.

Системную инструкцию обобщаем: она учитывает текстовые и голосовые запросы
с ответом текстом вместо предположения, что каждый запрос записан прибором.
Модель, инструменты, предел числа раундов и правила выполнения остаются общими.

Финальный текст отправляем в исходный чат ответом на исходное сообщение.
Длинные ответы разбиваем по лимиту Telegram без обрезания. Отправляем обычный
текст без интерпретации разметки, чтобы содержимое ответа не ломало отправку.
В одном чате запросы выполняются по порядку.

## Команда `/dashboard`

Команда вызывает тот же рендер в `dashboard.py` по текущим серверным снимкам
покупок и погоды, без Gemini и нового инструмента. Рендер выполняется вне
event loop. Результат — тот же однобитный PNG 800×480, что и для прибора.
Отправляем его файлом через `sendDocument`, сохраняя исходное изображение
для отладки.

Сейчас сервер не хранит батарейку, температуру и влажность: прибор передаёт
их в запросе `GET /sticky/dashboard`. При реализации сохраняем всю историю
полученных показаний в SQLite, как описано ниже. Для Telegram-рендера берём
последнее значение каждого показателя. До первого получения данных показываем
штатные обозначения неизвестных значений. В подписи указываем время показаний
либо их отсутствие; если времена различаются, показываем их отдельно.

Это свежий рендер, а не последний кадр, отправленный прибору. Покупки и погода
могли измениться, пока прибор спит. Даже сохранённый отправленный PNG не
подтвердил бы успешное обновление физического экрана. Хранение последнего PNG
и получение снимка физического экрана не входят в принятое решение.

## История показаний прибора

Решение уточнено 2026-10-08: сохраняем не только последние значения, но и все
полученные показания батарейки, температуры и влажности для последующего
анализа. Используем существующую SQLite по `DATABASE_PATH` на постоянном
томе Docker. История переживает перезапуск сервера и замену контейнера.

Добавляем отдельную таблицу `device_readings`: одна строка на полученное
значение одного показателя. Планируемые поля:

| Поле | Содержание |
| --- | --- |
| `id` | Целочисленный первичный ключ, разрешающий совпадения времени |
| `metric` | `battery_pct`, `temperature_c` или `humidity_pct` |
| `value` | Числовое значение; температура и влажность сохраняют дробную часть |
| `received_at` | Время получения сервером, Unix timestamp в UTC |

Все показания одного авторизованного и прошедшего валидацию запроса
`GET /sticky/dashboard` записываем одной транзакцией с общей меткой времени.
Это время получения, а не точное время измерения: прибор его пока не передаёт.
Пропущенные параметры не создают строк и не затирают предыдущие значения.
Запрос без показаний, в том числе просмотр из браузера, ничего не добавляет.
Рендер из Telegram только читает историю.

Повторяющиеся значения тоже сохраняем: они показывают, что прибор прислал
новые данные, даже если температура или заряд не изменились. Автоматической
очистки и агрегации истории в этой версии нет. Историю до включения этой
функции восстановить нельзя.

Добавляем индекс `(metric, received_at DESC, id DESC)` для быстрого получения
последнего значения каждого показателя через сортировку по времени и ID
с `LIMIT 1`. При одинаковом времени выбираем строку с большим ID.
Отдельный индекс `(received_at)` нужен для выборки всех показаний за период
при последующем анализе. Отдельную таблицу последних значений и глобальный
кеш не заводим: дашборд получает их из истории.

## Ошибки и повторы

Ошибки загрузки аудио, Gemini и отправки ответа обрабатываются адаптером
и не должны останавливать обслуживание прибора. Когда связь позволяет,
пользователь получает понятный текст ошибки. При неопределённом исходе
не утверждаем, что действие не выполнено.

Нужна защита от повторной обработки одного Telegram update. Ошибка отправки
финального ответа не запускает Gemini и инструменты заново: они могли уже
изменить Keep или создать напоминание. Повтор доставки готового ответа
отделён от выполнения команды.

Механизм учёта updates и восстановления после перезапуска выбираем при
реализации и проверяем тестами. Сам polling не гарантирует однократного
выполнения внешних действий при аварии процесса; такую гарантию не обещаем.

## План изменений и проверки

- `telegram_bot.py`: конфигурация, проверка допуска, обработчики текста,
  голосовых и `/dashboard`, ответы, ошибки и защита от повторов.
- `assistant.py`: общий вход для текста и аудио и обобщённая инструкция.
- `main.py`: жизненный цикл бота и сохранение показаний прибора.
- Общий путь рендера дашборда, таблица истории показаний в SQLite и индексы
  по показателю и времени; чтение последних значений из истории.
- `pyproject.toml`, `uv.lock`: зависимость `python-telegram-bot`.
- `docs/server.md`: настройки и фактическое поведение после реализации.

Прошивка и контракт `/audio` не меняются. Модуль в корне `server/` попадёт
в Docker-образ по существующему правилу копирования `*.py`.

Автономные тесты проверяют конфигурацию и выключенный бот, допуск до скачивания
и вызова модели, логирование неизвестного Chat ID без ответа пользователю
и без содержимого сообщения, текст и голос, лимит аудио, порядок сообщений, повторные
updates, ошибки и отсутствие повторного выполнения при сбое отправки ответа.
Для `/dashboard` проверяем PNG, общий рендер, последние показания и их отсутствие.
Для истории проверяем сохранение всех полученных значений, включая одинаковые,
дробные значения датчиков, частичные запросы, общую метку времени и атомарную
запись показаний одного запроса, выбор последних при совпадении времени,
сохранность после повторной инициализации базы и отсутствие записей от
запросов без показаний, неавторизованных и невалидных запросов.
Существующие тесты прибора должны продолжать проходить. Telegram, Gemini и Keep
в тестах подменяются, реальные секреты и сеть не используются.
