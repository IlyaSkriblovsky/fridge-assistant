# Замысел

Бэкенд персонального голосового ассистента. Запрос приходит голосом с прибора,
который висит на холодильнике. Ассистент понимает, что от него хотят, делает
это, в том числе во внешних сервисах, и отвечает коротким текстом. Прибор
показывает этот текст на экране.

## Прибор

Seeed reTerminal Sticky (E1005) — небольшой прибор на батарейке: ESP32-S3,
микрофон, пищалка, монохромный ePaper 800×480, три кнопки и магнит, на котором
он держится на холодильнике. Ещё на плате есть тач-панель и датчики
(температура и влажность, акселерометр, RTC). Прошивка уже читает батарею,
температуру и влажность и показывает их рядом с голосовым ответом.

Прошивка находится в [`firmware/`](../../firmware). Пользователь зажимает
кнопку, говорит, отпускает. Запись уходит на `POST /audio`, а ответ сервера
появляется на экране. Через 10 секунд после завершения отрисовки его заменяет
[дашборд на экране покоя](use-cases/idle-screen.md). Между обновлениями прибор
спит в deep sleep; эта реализация ещё ждёт аппаратной приёмки.

Как прибор и сервер разговаривают, описано в [device-contract.md](device-contract.md).

## Как это выглядит для пользователя

1. Заметил, что в холодильнике закончилось молоко. Зажал кнопку, сказал
   «добавь молоко в список покупок», отпустил.
2. Пищалка подтверждает, что вопрос принят, на экране появляется «Working».
3. Через несколько секунд на экране ответ, например что молоко добавлено.

Каждое голосовое нажатие — это один запрос и один ответ. Помимо кнопок прибор просыпается
по расписанию, заданному сервером. Сервер сам разбудить прибор не может.

## Решения

### Дашборд рисует сервер

Основа реализована 2026-09-22; 2026-09-23 пользователь подтвердил работу PNG на приборе. Сервер готовит
монохромный проверочный кадр 800×480 с показаниями, присланными прибором.
Содержание и внешние источники будут отдельным этапом. Единственный формат
передачи — однобитный PNG без параметра выбора формата. Прибор показывает кадр при включении,
по таймеру и через 10 секунд после завершения отрисовки голосового ответа.
На время паузы сохраняет Wi-Fi; голосовое нажатие имеет приоритет.

Базовый период — час, следующий запрос назначает заголовок
`Next-Update-After`. При сбое сохраняется прежний экран, для неактуальности
предусмотрен небольшой индикатор. Дизайн и состав дашборда выбираются
отдельно; замеры сжатия и энергопотребления, а также автономные напоминания
отложены. Подробный план — в [idle-screen.md](use-cases/idle-screen.md),
формат обмена — в [device-contract.md](device-contract.md#дашборд).

### Один пользователь, один прибор, один токен

Проект для личных целей, прибор существует в единственном экземпляре. Поэтому
сервер не различает пользователей, и учётных записей у него нет. Несколько
пользователей пока не рассматриваем.

Сервер доступен из интернета, так что домашний WiFi больше не граница
доверия. Прибор предъявляет статичный токен в `Authorization: Bearer`, и тот
же токен лежит в настройках сервера. Для одного прибора этого достаточно:
не нужны ни выдача токенов, ни их срок жизни, ни обмен. Сменить токен — значит
поменять его в обоих местах и перепрошить прибор.

Пока прибор ходит по HTTP, токен идёт открытым текстом, и его может прочитать
любой, кто видит трафик по дороге. От тех, кто просто нашёл адрес сервера, он
защищает, а это самый вероятный гость. Замеры E2 завершены; 2026-09-23 пользователь решил пока
сохранить HTTP и отложить переход на HTTPS, см.
[deferred.md](deferred.md#https-между-прибором-и-сервером). Ещё токен можно прочитать из флеша
прибора, как и остальное в его `src/secrets.h`.

### Голос и команды обрабатывает Gemini API

Запись с прибора уходит в Gemini API методом `generateContent` вместе с
описаниями функций, которые может вызывать ассистент, например «добавить в
список покупок». Модель сама распознаёт речь, решает, что сделать, и вызывает
функции. Сервер выполняет вызовы и возвращает модели результат, а её последний
текстовый ответ отправляет на прибор. Модель по умолчанию —
`gemini-3.5-flash-lite`.

Почему так:

- **Подписки на Claude и ChatGPT не покрывают API.** У обоих API оплачивается
  отдельно, а вход через подписку предназначен для их собственных приложений.
  Запускать из сервера `claude -p` или `codex exec` под подпиской — серая зона.
  К тому же это медленно и расходует лимиты подписки.
- **Gemini сам принимает звук.** Claude звук не принимает, и перед ним
  пришлось бы отдельно распознавать речь. Gemini распознаёт русскую речь и
  вызывает функции в одном запросе.
- **У Gemini API есть бесплатный уровень**, и он не связан с подпиской: в
  Google One Basic ничего про Gemini нет. Если бесплатного уровня не хватит,
  платный стоит доли цента за запрос.
- **Flash Lite хватает.** В пробном прогоне на записях с прибора
  (`experiments/gemini_audio.py`) `gemini-3.5-flash-lite` правильно разобрал,
  что добавить в список, и вызвал функцию. Первый раунд занял 1,7 с и 344
  токена. `gemini-3.8-flash` в тот момент не отвечал.

Почему `generateContent`, а не Live API:

- Меньше движущихся частей: обычный запрос вместо WebSocket-сессии, и ответ
  приходит текстом.
- Модели Live API отвечают только голосом. Текст для экрана пришлось бы брать
  из расшифровки их речи.
- Вопрос длится несколько секунд, поэтому потоковая передача выиграла бы
  немного.

Чем за это платим: звук уходит в Gemini только после того, как тело запроса
пришло целиком. Потоковую передачу, которую позволяет
[контракт с прибором](device-contract.md#звук-приходит-потоком), сервер пока
не использует. Files API для записи не нужен: запрос может весить до 20 МБ,
а это около восьми минут звука.

К Live API стоит вернуться, если ждать ответа окажется слишком долго. Он
принимает звук потоком ровно в том формате, который шлёт прибор (PCM, 16 бит,
16 кГц), распознаёт речь, пока человек говорит, и тоже умеет вызывать функции.

### Бесплатный уровень Gemini API

Сервер работает на бесплатном уровне Gemini API. Google использует запросы и
ответы бесплатного уровня для улучшения своих продуктов, и их могут читать
люди. Для нас это записи голоса из дома, но ничего секретного с прибором не
обсуждают, так что это приемлемо. Лимитов бесплатного уровня на десятки
запросов в день, скорее всего, хватит. В ЕЭЗ, Швейцарии и Великобритании и на
бесплатном уровне действуют условия платного.

Платный уровень данные для обучения не использует и стоит доли цента за
запрос. На него стоит перейти, если упрёмся в лимиты или с прибором начнут
обсуждать то, что не должно попасть к Google.

### Записи не хранятся

Запись с прибора копится в памяти, уходит в Gemini и выбрасывается. На диск
сервер её не пишет. Прототип сохранял записи только для отладки. Теперь для
разбора неудачных запросов сервер пишет в лог, что модель поняла и что
сделала.

### Сервер живёт на арендованном сервере

Сервер работает в Docker на арендованном сервере пользователя, за
nginx-proxy, который там уже обслуживает другие проекты. Образ собирает CI из
этого репозитория и публикует в GHCR. Как это устроено, описано в
[server.md](server.md#деплой).

Страна этого сервера должна быть в
[списке регионов Gemini API](https://ai.google.dev/gemini-api/docs/available-regions).
Судя по документации, проверяется страна машины, которая делает запрос.
России и Беларуси в списке нет.

Из интернета сервер доступен, и прибор предъявляет ему токен
([выше](#один-пользователь-один-прибор-один-токен)). HTTPS у прибора пока нет,
переход отложен после E2, см.
[deferred.md](deferred.md#https-между-прибором-и-сервером).
