# Замысел

Бэкенд персонального голосового ассистента. Запрос приходит голосом с прибора,
который висит на холодильнике. Ассистент понимает, что от него хотят, делает
это, в том числе во внешних сервисах, и отвечает коротким текстом. Прибор
показывает этот текст на экране.

## Прибор

Seeed reTerminal Sticky (E1005) — небольшой прибор на батарейке: ESP32-S3,
микрофон, пищалка, монохромный ePaper 800×480, три кнопки и магнит, на котором
он держится на холодильнике. Ещё на плате есть тач-панель и датчики
(температура и влажность, акселерометр, RTC), но прошивка их пока не использует.

Прошивка — отдельный проект, локально он лежит рядом, в `../sticky-test-2`.
Она почти готова: пользователь зажимает кнопку, говорит, отпускает. Запись
уходит на `POST /audio`, а ответ сервера появляется на экране и остаётся там до
следующего вопроса. Между вопросами прибор спит в deep sleep.

Как прибор и сервер разговаривают, описано в [device-contract.md](device-contract.md).

## Как это выглядит для пользователя

1. Заметил, что в холодильнике закончилось молоко. Зажал кнопку, сказал
   «добавь молоко в список покупок», отпустил.
2. Пищалка подтверждает, что вопрос принят, на экране появляется «Working».
3. Через несколько секунд на экране ответ, например что молоко добавлено.

Каждое нажатие — это один запрос и один ответ. Сам сервер ничего показать на
приборе не может: прибор спит и просыпается только от кнопки.

## Решения

### Один пользователь, один прибор, без авторизации

Проект для личных целей, прибор существует в единственном экземпляре. Поэтому
в запросе с аудио нет никакой авторизации, и сервер не различает
пользователей. Несколько пользователей и авторизацию пока не рассматриваем.

Сейчас граница доверия — домашний WiFi. Сервер слушает в локальной сети, и
тот, кто до него дотянулся, уже в сети. Если сервер уедет из LAN, вопрос
придётся открыть заново, и авторизация придёт вместе с HTTPS: токен по
открытому HTTP хуже, чем никакого. В прошивке это отложенные пункты D5 и D8.

### Голос и команды обрабатывает Gemini API

Запись с прибора уходит в Gemini API методом `generateContent` вместе с
описаниями функций, которые может вызывать ассистент, например «добавить в
список покупок». Модель сама распознаёт речь, решает, что сделать, и вызывает
функции. Сервер выполняет вызовы и возвращает модели результат, а её последний
текстовый ответ отправляет на прибор. Модель по умолчанию —
`gemini-3.5-flash-lite`.

Почему так:

- **Подписки на Claude и ChatGPT не покрывают API.** У обоих API оплачивается
  отдельно, а вход через подписку предназначен для их собственных приложений.
  Запускать из сервера `claude -p` или `codex exec` под подпиской — серая зона.
  К тому же это медленно и расходует лимиты подписки.
- **Gemini сам принимает звук.** Claude звук не принимает, и перед ним
  пришлось бы отдельно распознавать речь. Gemini распознаёт русскую речь и
  вызывает функции в одном запросе.
- **У Gemini API есть бесплатный уровень**, и он не связан с подпиской: в
  Google One Basic ничего про Gemini нет. Если бесплатного уровня не хватит,
  платный стоит доли цента за запрос.
- **Flash Lite хватает.** В пробном прогоне на записях с прибора
  (`experiments/gemini_audio.py`) `gemini-3.5-flash-lite` правильно разобрал,
  что добавить в список, и вызвал функцию. Первый раунд занял 1,7 с и 344
  токена. `gemini-3.8-flash` в тот момент не отвечал.

Почему `generateContent`, а не Live API:

- Меньше движущихся частей: обычный запрос вместо WebSocket-сессии, и ответ
  приходит текстом.
- Модели Live API отвечают только голосом. Текст для экрана пришлось бы брать
  из расшифровки их речи.
- Вопрос длится несколько секунд, поэтому потоковая передача выиграла бы
  немного.

Чем за это платим: звук уходит в Gemini только после того, как тело запроса
пришло целиком. Потоковую передачу, которую позволяет
[контракт с прибором](device-contract.md#звук-приходит-потоком), сервер пока
не использует. Files API для записи не нужен: запрос может весить до 20 МБ,
а это около восьми минут звука.

К Live API стоит вернуться, если ждать ответа окажется слишком долго. Он
принимает звук потоком ровно в том формате, который шлёт прибор (PCM, 16 бит,
16 кГц), распознаёт речь, пока человек говорит, и тоже умеет вызывать функции.
