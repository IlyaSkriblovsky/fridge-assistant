# Assistant Server

Прототип серверной части для AI-ассистента на Seeed Sticky (reTerminal E1005).
Пока умеет одно: принять WAV с прибора и положить его на диск.

## Запуск

```sh
uv sync
uv run python main.py
```

При старте печатает адрес, который нужно вписать в прибор:

```
  Put this URL into the device (same WiFi network):
    http://192.168.1.42:8000/audio
  Public IP (needs port forwarding to be reachable): 203.0.113.7
```

Прибор в той же WiFi-сети ходит по локальному адресу. Публичный IP печатается
на случай, если понадобится доступ снаружи — сам по себе он не заработает, нужен
проброс порта на роутере.

Переменные окружения: `HOST` (по умолчанию `0.0.0.0`), `PORT` (`8000`),
`RECORDINGS_DIR` (`recordings`).

## Эндпоинт

`POST /audio` — тело запроса это WAV. Content-Type не проверяется; multipart-форма
с файлом тоже принимается, если прошивке так удобнее.

Прибор шлёт тело потоком (`Transfer-Encoding: chunked`), пока кнопка ещё
зажата, поэтому длина записи в момент отправки заголовка неизвестна: оба поля
длины в WAV-заголовке приходят как `0xFFFFFFFF`. Сервер вписывает настоящие
длины, когда тело пришло целиком, — или когда поток оборвался, тогда в файле
то, что успело прийти.

Файл сохраняется как `recordings/YYYYMMDD-HHMMSS-mmm.wav`. Ответ:

```json
{
  "status": "ok",
  "filename": "20260915-163045-123.wav",
  "bytes": 64044,
  "response": "Received 64044 bytes"
}
```

В консоль пишется размер и разобранный WAV-заголовок — так видно, с какими
параметрами прибор реально пишет звук:

```
[20260915-163045-123] 20260915-163045-123.wav  64044 bytes chunked over 2.31 s  content-type=audio/wav  16000 Hz, 1 ch, 16-bit, 2.00 s  (lengths filled in)
```

Если заголовка нет (сырой PCM), в логе будет `not a readable WAV` — файл всё
равно сохранится.

## Проверка

```sh
curl -X POST --data-binary @sample.wav -H "Content-Type: audio/wav" \
  http://localhost:8000/audio
```

## Намеренные сбои

Прошивка различает четыре плохих исхода запроса — `NO SERVER`, `SERVER ERROR`,
`BAD RESPONSE`, `TIMED OUT` — и три из них невозможно получить от сервера,
который работает. Для этого есть три эндпоинта; они ничего не сохраняют:

| Эндпоинт | Что делает | Что показывает прибор |
| --- | --- | --- |
| `POST /audio/fault/500` | Отвечает `500` | `SERVER ERROR 500` |
| `POST /audio/fault/empty` | Отвечает `200` и `{}` | `BAD RESPONSE` |
| `POST /audio/fault/slow` | Молчит `FAULT_DELAY_SECONDS` (45 с) | `TIMED OUT` |

`NO SERVER` сервер не нужен вовсе: прошивка сама стучится на закрытый порт и на
адрес, где никого нет.

Тело запроса дочитывается до конца перед ответом — иначе соединение закроется
под прибором, который ещё не закончил загрузку, и он покажет `NO SERVER` вместо
проверяемого случая.
